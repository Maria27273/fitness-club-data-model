# Проектирование базы данных

Для реализации модели данных используется реляционная база данных **PostgreSQL**.

Проектирование выполнено с учетом требований предметной области и бизнес-правил, определенных на предыдущих этапах анализа.

Основные задачи проектирования:

* обеспечить целостность и непротиворечивость данных
* исключить дублирование информации
* корректно реализовать связи между сущностями

---

## Нормализация данных

При проектировании используется нормализованная реляционная модель. Структура приведена к **третьей нормальной форме (3NF)**.

---

## Первичные и внешние ключи

Для каждой сущности используется первичный ключ

| Таблица      | Первичный ключ  | Назначение               |
| ------------ | --------------- | ------------------------ |
| `client`     | `client_id`     | идентификация клиента    |
| `trainer`    | `trainer_id`    | идентификация тренера    |
| `session`    | `session_id`    | идентификация занятия    |
| `membership` | `membership_id` | идентификация абонемента |
| `booking`    | `booking_id`    | идентификация записи     |
| `attendance` | `attendance_id` | идентификация посещения  |
| `equipment`  | `equipment_id`  | идентификация тренажёра  |

Внешние ключи используются для обеспечения ссылочной целостности:

* `membership.client_id → client.client_id`
* `session.trainer_id → trainer.trainer_id`
* `booking.client_id → client.client_id`
* `booking.session_id → session.session_id`
* `attendance.booking_id → booking.booking_id`

Связь между `booking` и `attendance` дополнительно ограничивается уникальностью `booking_id`. Это означает, что для одной записи на занятие может существовать не более одной записи о фактическом посещении.

## Ограничения целостности

Для предотвращения некорректных данных используются ограничения нескольких типов

### NOT NULL

`NOT NULL` используется для обязательных атрибутов

Например:

* имя клиента
* дата рождения
* тип занятия
* время начала занятия
* максимальное количество участников
* идентификаторы связанных сущностей

Это не позволяет создать запись без обязательной информации

### UNIQUE

Ограничение `UNIQUE` используется для атрибутов, значения которых должны быть уникальными.

Для клиента:

* номер телефона
* адрес электронной почты

Для посещения:

* `booking_id`

При этом для активных записей и абонементов используются частичные уникальные индексы, так как бизнес-правила требуют уникальности только для определенных состояний.

### CHECK

`CHECK` используется для проверки допустимых значений.

Примеры:

* стаж тренера не может быть отрицательным
* продолжительность занятия должна находиться в допустимом диапазоне
* количество участников должно быть положительным
* количество оставшихся посещений не может быть отрицательным

## Реализация бизнес-правил на уровне БД

Не все бизнес-правила могут быть реализованы с помощью стандартных `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE` и `CHECK`.

Для сложных правил, зависящих от нескольких записей или времени, используются:

* частичные уникальные индексы
* триггеры
* процедуры
* проверки при выполнении операций
* плановое выполнение процедур для правил, связанных с датой

### BR-01. Один активный абонемент на клиента

Один клиент может иметь несколько абонементов в течение всего периода обслуживания, но одновременно активным может быть только один.

Для этого используется частичный уникальный индекс по `client_id` для записей со статусом `активен`.

Таким образом, исторические абонементы сохраняются, но создать второй активный абонемент для одного клиента невозможно.

### BR-02. Дата окончания не раньше даты начала

Проверяется ограничением `CHECK`:

`end_date >= start_date`.

Это предотвращает создание абонемента с некорректным периодом действия.

### BR-03. Автоматическое завершение абонемента

После наступления `end_date` абонемент должен получить статус `закончен`.

Такое правило нельзя надежно реализовать обычным `CHECK`, поскольку статус должен изменяться с течением времени без изменения самой записи.

Для этого используется плановое выполнение процедуры обновления статусов. Запуск может осуществляться через планировщик на стороне БД или приложения.

### BR-04. Завершение разового абонемента после посещения

Для разового абонемента используется поле `visits_remaining`.

При подтвержденном посещении значение уменьшается с `1` до `0`, после чего абонемент переводится в статус `закончен`.

Операция выполняется в рамках обработки посещения

### BR-05. Запись только при наличии действующего абонемента

Перед созданием подтвержденной записи необходимо проверить:

* наличие у клиента абонемента
* статус абонемента `активен`
* соответствие даты занятия периоду действия абонемента

Проверка выполняется при создании записи

### BR-06. Ограничение количества участников

Количество подтвержденных записей на занятие не должно превышать значение `max_participants`.

При создании новой подтвержденной записи выполняется проверка текущего количества участников.

Если лимит достигнут, новая запись не создается.

### BR-07. Не более одной активной записи клиента на занятие

Для одного клиента может существовать не более одной активной записи на конкретное занятие.

В качестве активной записи рассматривается запись со статусом `подтверждена`.

Для контроля используется частичный уникальный индекс по:

* `client_id`
* `session_id`

только для записей со статусом `подтверждена`.

При этом отмененные записи сохраняются в истории и не препятствуют повторной записи клиента.

### BR-08. Отсутствие пересечения занятий у клиента

Клиент не может быть записан на два занятия, время которых пересекаются.

Время окончания занятия не хранится отдельно, а рассчитывается на основании: `start_time + duration_minutes`.

При создании подтвержденной записи проверяется пересечение нового занятия с другими подтвержденными записями клиента.

### BR-09. Отсутствие пересечения занятий у тренера

Тренер не может проводить два занятия одновременно.

При создании или изменении занятия проверяется отсутствие пересечения его временного интервала с другими занятиями этого тренера.

Для PostgreSQL данное правило может быть реализовано с использованием ограничения исключения по временному диапазону.

### BR-10. Ограничение возраста клиента

Для самостоятельного посещения занятия клиент должен быть старше 14 лет.

Возраст определяется на основании `birth_date`.

Проверка выполняется при создании записи на занятие, поскольку возраст зависит от даты операции и контекста посещения.

### BR-11. Запрет удаления клиента при будущих записях

Удаление клиента не должно приводить к потере информации о будущих записях.

Перед удалением проверяется наличие будущих подтвержденных записей.

При их наличии операция удаления запрещается.

Исторические данные должны сохраняться.

### BR-12. Запрет удаления тренера при запланированных занятиях

Тренер не может быть удален, если за ним закреплены будущие занятия.

Перед удалением выполняется проверка наличия таких занятий.

### BR-13. Запрет удаления занятия при подтвержденных записях

Занятие нельзя удалить, если на него существуют подтвержденные записи.

Это позволяет сохранить целостность данных о посещениях и истории записей.

---

## Стратегия удаления данных

Для основных сущностей не используется каскадное удаление (`ON DELETE CASCADE`), если оно может привести к потере истории

Например, удаление клиента не должно автоматически удалять:

* его абонементы
* историю записей
* информацию о посещениях

Вместо физического удаления для объектов, которые участвуют в исторических данных, предпочтительно использовать блокировку удаления

Это позволяет сохранить историю работы клуба и использовать ее для аналитики
